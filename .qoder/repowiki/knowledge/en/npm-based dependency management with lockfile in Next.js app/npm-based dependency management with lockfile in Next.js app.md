## System / Approach

This repository uses **npm** as the package manager for a single Next.js application located under `Next-app/`. Dependencies are declared in `package.json` and resolved against the public npm registry. A `package-lock.json` (lockfileVersion 3) is committed alongside the manifest, pinning exact transitive versions to ensure reproducible installs.

There is no vendoring of third-party packages — `node_modules/` is present but ignored by `.gitignore`, so dependencies are installed on demand rather than checked in.

## Key files

- `Next-app/package.json` — declares runtime `dependencies` and `devDependencies`, plus npm scripts (`dev`, `build`, `start`, `lint`).
- `Next-app/package-lock.json` — deterministic lockfile generated by npm; records every resolved package, version, integrity hash, and dependency tree.
- `Next-app/.gitignore` — excludes `node_modules/`, keeping the repo free of vendored code.
- `Next-app/eslint.config.mjs` — linting configuration consumed via the `eslint` devDependency.
- `Next-app/tsconfig.json` — TypeScript compiler options consumed via the `typescript` devDependency.
- `Next-app/postcss.config.mjs` — PostCSS pipeline driven by `tailwindcss` and `@tailwindcss/postcss` devDependencies.
- `Next-app/drizzle.config.ts` — Drizzle ORM configuration used by the `drizzle-kit` devDependency.

## Architecture and conventions

- **Single project scope**: All dependencies live in one `package.json`; there are no workspaces or monorepo tooling.
- **Runtime vs. build-time split**: Runtime libraries (Next.js, React, Supabase client, Drizzle ORM, Zustand, Tailwind utilities, Lucide icons) are listed under `dependencies`; tooling (TypeScript, ESLint, Tailwind CSS v4, Drizzle Kit, Postgres driver, dotenv) is listed under `devDependencies`.
- **Version ranges**: Most packages use caret (`^`) ranges (e.g. `^0.12.5`, `^2.112.4`, `^5.102.8`), allowing minor/patch updates while preserving major-version compatibility. A few core packages (`next`, `react`, `react-dom`, `eslint-config-next`) are pinned to exact versions matching each other to avoid peer-dependency mismatches.
- **Lockfile-driven installs**: Because `package-lock.json` is committed, `npm ci` or `npm install` will resolve to the exact versions recorded in the lockfile, overriding any semver range changes in `package.json` until the lockfile is regenerated.
- **No private registry or proxy**: The lockfile entries resolve from `https://registry.npmjs.org/`; there is no `.npmrc` or equivalent file visible in the repo to configure a private registry, authentication token, or scoped package mirror.
- **Scripts as the entry point**: Dependency consumption is primarily through npm scripts (`next dev`, `next build`, `next start`, `eslint`) rather than custom build tooling.

## Conventions and constraints

- **Declare only what is needed**: Runtime-only packages go in `dependencies`; development-only tooling goes in `devDependencies`. This keeps production builds lean.
- **Pin framework peers together**: `next`, `react`, `react-dom`, and `eslint-config-next` share the same major/minor version (`16.x` / `19.x`), which is required by Next.js peer dependency rules.
- **Use caret ranges for ecosystem packages**: Third-party libraries use `^` ranges, accepting automatic minor/patch bumps while protecting against breaking major upgrades.
- **Commit the lockfile**: `package-lock.json` is tracked in version control, making installs deterministic across environments and CI.
- **Do not commit `node_modules`**: The directory is gitignored, so contributors must run `npm install` locally before developing.
- **No vendoring or offline cache strategy**: There is no `vendor/`, `lib/`, or local copy of npm packages; all resolution happens at install time from the npm registry.
